## 0. 総評

### 0.1 結論

**設計思想は妥当。壊れているのは計画の構造。**

技術的な中核判断（正史をモデル外に置く、状態変更と文章を分離する、実装は交換可能でも意味論は交換不能とする）は、現在のLLMでTRPGを成立させる方向として正しい。ここに大きな異論はない。

問題は次の3点に集約される。

**(1) 最も不確実なリスクを最後に検証する順序になっている。**
Phase 0の完了条件4項目はすべて「正しさ」の検査で、「遊んで面白かったか」が1つも入っていない。そして§18のPhase 0成果物リストには、実際に遊んで退屈になる要因（テンポ、文章量、選択肢の提示、NPCの能動性、直近の状況表示）に対応するものが1つも含まれない。Phase 0を完璧に終えても、このプロダクトが面白いかどうかは何も分からない。これは「自分が遊びたい」という目的に対して致命的な順序である。

**(2) 「Narratorが新しい事実を作らない」という中核の不変条件が、運用不能な形で定義されている。**
§9.3の禁止リスト方式は、TRPGの描写では原理的に守れない。かつ、守れているかどうかを判定する方法が文書のどこにもない。これはCore Contractの変更を要する（§I-2）。

**(3) 正史の権威が Event Log と Canon Ledger に二重化しており、責務境界が決まっていない。**
§23-4が自ら問うている論点だが、文書内では未解決のまま両方が「権威ある記録」とされている。ここを決めないと、Canon Ledgerの実装が際限なく膨らむ（§I-4）。

### 0.2 スコープの規模感

§19「含める」21項目を文書の仕様どおりに実装した場合の規模を、雑に見積もる。桁が合っていれば十分という前提。

| 分類 | 該当項目 | 支配的なコスト要因 |
|---|---|---|
| 数日 | ダイス、セーブ/ロード、サーバー側APIキー | — |
| 数週間 | Event Log、State Projection、Model Provider、Web、Telemetry、Profile | — |
| 数ヶ月 | Canon Ledger、Recall Gate、Reference Ruleset、検証Scenario、Replay | §10.2 L2の11概念、§10.5の回想クエリ検出、§17.1の14項目追跡、§12.1のシナリオ構造 |

**注意すべきは、この見積もりが「文書の仕様どおりに実装した場合」である点。**

§18 Phase 0 の成果物は「Event / Canon / Stateの**最小実装**」と書かれている。しかし**その「最小」が何を指すかが、文書内で定義されていない。** Canon Ledgerの唯一の定義は§10.2 L2の11概念（安定Entity ID、Subject/Predicate/Value、Record Kind、Epistemic Status、Authority、Visibility、Effective From/Until、Source Event/Transcript、Supersedes、Revision、Current Status）であり、実装者はそこへ引きずられる。これは実質的に二時間軸（bitemporal）の知識ベースである。Recall Gate（§10.5）も、6状態の分岐と可視性フィルタと証拠検証を含む。

**この2つがPhase 0の規模を決める。** そして両方とも、Canonが数百件のうちは、より軽い代替（可視性でフィルタしたCanonをプロンプトへ入れ、Evidence IDの引用を検証する方式。§V-2）で機能的に置き換えられる。**後から本来の形へ拡張するのは、列を足すマイグレーションで済む。** つまり高いのは「最初から完全形を作ること」であって、機能そのものではない。§V-2はこの前提に立っている。

「自分が遊びたい」という目的に対しては、**削るべきは機能ではなく「初めて通しで遊べるまでの時間」**である。具体案は §V に書く。

### 0.3 評価できる点（お世辞ではなく、削らない方がよい判断として）

- **§5.3（プロンプトで頼むこととコードで強制することを分ける）** — この線引きが最初から引けているのは大きい。ここが曖昧なプロジェクトは必ず破綻する。
- **§9.2（Semantic Resultと自由文の分離）** — 実装を最小化してもこの一点だけは譲るべきでない。後から自由文をパースする羽目になると回復不能。
- **§10.1（Summary/Index/Cacheは再生成可能でなければならない、CanonとEventはそれらに依存しない）** — この規律は追加コストがほぼゼロで、効果が非常に大きい。§20-7はこの規律の直接のテストになっており、受け入れ条件20項目の中で最も費用対効果が高い。
- **§5.10（フレームワークを先に完成させない）と§21.1** — 自己認識として正確。ただし後述するとおり、計画本体がこの原則に従っていない（§II-3, §V-3）。
- **§10.4のL4（世界の真実／PCの知識／NPCの信念／噂の分離）** — AI GMの価値が最も出る部分を正しく特定している。ここは削らない方がよい。

## I-1. Phase 0の完了条件に「面白かったか」がなく、最も不確実なリスクを最後に検証する順序になっている

### 何が問題か

§18 Phase 0の完了条件は次の4項目である。

> - 長い入力列でも確定事項を根拠付きで回答できる
> - 未決定事項を捏造しない
> - 状態をEventから再構築できる
> - モデル失敗で半端な状態を残さない

4項目すべてが「正しさ」の検査であり、「遊んで面白かったか」の判定がない。面白さの評価は§17.3で扱われるが、そこに至るのは§18のPhase 1以降である。

さらに、実際にプレイして退屈・疲労の原因になる要因は、Phase 0の成果物リストに1つも含まれていない。

| 退屈・疲労の要因 | 文書での扱い | Phase 0成果物 |
|---|---|---|
| 1ターンの待ち時間が長い | 原則（§5.7）・リスク（§21.6）・指標（§17.2）としては扱われている。ただし体感速度を作る実装（Streaming）は§7.3と§15.1に語があるだけ | なし |
| GMの文章が長すぎて読み飛ばす | §13.3の「文章量」プリセット | なし |
| 何を入力していいか分からない | §13.2の `option_explicitness` | なし |
| NPCが受け身で世界が動かない | §12.2のClock、§13.2の `npc_initiative` | なし |
| 直近3〜10ターンの状況を見失う | §20-2は「500Turn前」を目標に置く | なし |
| 現在の状況（場所・所持品・目的）が分からない | §7の図にCharacterパネル、§10.2 L3に所持品・位置。ただし常時表示という要件は未記述 | なし |

**Phase 0を完璧に終えても、このプロダクトが面白いかどうかは何も分からない。** そして§18 Phase 0はCanon Ledger、Recall Gate、Replay、Turn Plannerを含むため、最も重い段階でもある。

なお、文書は §1 で現行LLMの弱点を8つ挙げ、§21 でリスクを9件挙げているが、**「作ったが面白くなかった」というリスクが両方に入っていない。** §21には技術リスクだけでなく進行リスク（§21.1 プラグイン基盤の過剰設計）も法務リスク（§21.8）も含まれているので、リスクの種類が偏っているのではなく、**体験そのものを対象にしたリスクだけが欠けている。**

### どの状況で問題になるか

Canon LedgerとRecall Gateを実装し終えて初めて通しでプレイし、そこで「文章が長くて読み飛ばす」「NPCが何もしてこない」「選択肢が思いつかず手が止まる」と分かる状況。これらの修正はCanon Ledgerとは無関係な領域（プロンプト、UI、Clock）にあり、Phase 0で払ったコストは体験改善に一切寄与していない。

特に §18 Phase 0 の成果物には「CLIまたはHeadless Runner」が含まれる。**この時点で既に遊べる。** つまり面白さの検証はPhase 0の途中で可能なのに、完了条件がそれを要求していない。

### Core Contractを変更すべきか

不要。Contractの問題ではなく、Phase定義の問題。

### v0.1で対応すべきか

**対応すべき。というより、これが最優先。**

### 推奨する修正案

1. **§18 Phase 0の完了条件に次を追加する。**
   > - 実装者本人がCLIで最初から最後まで通しで遊び、翌日もう一度遊びたいと思った

   思わなかった場合、Canon Ledgerを作り込む前に判明したことが最大の成果になる。

2. **§21にリスクを1件追加する。**
   > ### 21.10 遊んで面白くない
   > **リスク**: 正しさの条件をすべて満たしたが、テンポ、文章量、選択肢の乏しさ、NPCの受動性により、遊んで退屈になる。
   > **対策**:
   > - Phase 0のCLI段階で通しプレイを行い、完了条件に含める
   > - 退屈要因（待ち時間、文章量、選択肢提示、NPC能動性、現在状況の可視化）を明示的な設計対象とし、§13.2の内部パラメータではなく実装項目として扱う

3. **§18 Phase 0の成果物に、体験側の最小項目を追加する。** いずれも数時間規模で、Canon Ledgerより桁違いに安い。
   - 出力のStreaming表示（体感速度）
   - GM応答の長さ上限（プロンプト側の制約でよい）
   - ターン末の選択肢サジェスト2〜4個
   - クロック1本（Nターンごとに敵対勢力が1歩進む）
   - 現在の場所・所持品・HP・目的の常時表示

## I-2. 「Narratorが新しい事実を追加しない」という不変条件が、禁止リスト方式では運用不能

### 何が問題か

§9.3はNarratorに対する禁止リストを置いている。

> Narratorは、次を独自に追加してはならない。
> - 新しい固有名詞
> - 新しい出入口
> - 使用可能な物品
> - 手掛かり
> - 数量
> - 約束
> - 関係変化
> - ルール効果
> - 状態変化
> - NPCが知る新情報

そして許可範囲を次のように定める。

> Narratorが追加できるのは、既存の意味を変えない文体、リズム、比喩、非拘束的な感覚描写に限る。

これは3つの意味で成立しない。

**(a) 描写が原理的に書けなくなる。**
「宿屋に入った」という状況をCanonに登録された要素だけで描写するには、テーブル、椅子、暖炉、酒瓶、店主の外見、匂い、音がすべて事前にCanonへ登録されている必要がある。登録されていなければ、Narratorは「あなたは宿屋に入った。」以上のことを書けない。実際には、Narratorは常に新しい名詞を生成する。これはプロンプトで抑制できる種類の問題ではない。

**(b) 分類が公開時点では原理的に決まらない。**
§10.3は分類基準をこう書く。

> 比喩、リズム、雰囲気だけを目的とした非拘束的描写はTranscriptに残し、原則としてCanon化しない。

しかし「行動根拠になり得るか」は**将来のプレイヤー行動に依存する**。「窓から月明かりが差し込む」は雰囲気描写のつもりでも、プレイヤーが「窓から出る」と言った瞬間に出入口になる。「埃をかぶった本棚がある」は、調べられた瞬間に手掛かりの容器になる。公開時点で「これは非拘束的描写である」と判定することはできない。

**(c) §5.6と§9.3が、この分類不能性のために衝突する。**

> §5.6: 名前、場所、物品、約束、手掛かり、関係、数値、ルール裁定など、後の行動根拠になる事実は、公開と同じターンで記録する。
> §9.3: 装飾的描写をプレイヤーが後から明示的に行動へ利用した場合は、Transcriptを根拠に、矛盾確認後にCanonへ昇格できる。

後から行動に使われた描写は、定義上「後の行動根拠になる事実」だったのに同ターンで記録されなかったものであり、§5.6の違反事例そのものである。§9.3の後半は、§9.3の前半（不変条件）が守られなかった場合の事後救済であり、実質的に不変条件を無効化している。

そして**§20-9「Narratorが新しい行動可能物を勝手に追加しない」の判定手法が定義されていない。**

§7.2の「NarrativeとSemantic Resultの整合性確認」が最も近いが、これでは判定できない。§9.2のSemantic Resultには「Narrativeで言及した要素」を表すフィールドがないため、**照合の相手が存在しない。** 追加された要素は、どのフィールドとも突き合わせられない。判定手法のない受け入れ条件は、受け入れ条件として機能しない。

### どの状況で問題になるか

ほぼ毎ターン。特に、プレイヤーが描写内の要素に言及したとき。

- 却下すれば、プレイヤーのAgencyを潰す（§26「選択に意味があり」に反する）
- 昇格させれば、「Narratorが出入口を追加したこと」を事後承認しているだけで、§9.3の不変条件は形骸化する
- 昇格の判定主体（誰が矛盾確認をするのか）と、矛盾したときの挙動が未定義

### Core Contractを変更すべきか

**変更すべき。** これは§14.3のContract本体に触れる。

### v0.1で対応すべきか

**対応すべき。** 後から方式を変えると、NarratorのプロンプトとSemantic Resultのスキーマの両方を作り直すことになる。

### 推奨する修正案

**禁止（prohibition）から捕捉義務（capture）へ、規範の向きを反転させる。**

新方針:

> Narratorは新しい名詞を出してよい。ただし、出力に現れた新規の名詞・数量・場所は、同じTurn内で `provisional_detail`（暫定詳細）として記録されなければならない。`provisional_detail` はプレイヤーが行動根拠として参照した時点で、矛盾確認のうえ通常のCanonへ昇格する。昇格が既存Canonと矛盾する場合のみ、GMは明示的に打ち消す。

**この提案が§9.3末尾の既存機構と何が違うのか（自分でここを詰めておく必要がある）**

正直に書くと、「後から参照されたら昇格する」という遅延昇格の仕組み自体は、§9.3末尾の記述と同じである。将来のプレイヤー行動に依存する判定は温存されている。**変わるのは規範の向きと、その検証可能性である。**

| | 原文 §9.3 | 本提案 |
|---|---|---|
| 規範 | Narratorは新事実を出して**はならない** | Narratorが出した新事実は必ず**記録される** |
| 判定可能性 | 「行動可能物か否か」の判定が必要。公開時点では原理的に決まらない（§20-9が測れない） | 「列挙されたか否か」の判定。**Narrativeの名詞と `mentioned_details` を突き合わせればよい** |
| 昇格時の根拠 | Transcript（全文検索が必要） | 構造化された `provisional_detail` レコード（IDで引ける） |
| I-3のPush型照合 | 既知Entityに登録されていないため照合できない | 暫定詳細も照合の対象になる |

**規範が判定不能なままでは、Contractに書いても意味がない。** 本提案の眼目は、判定不能な禁止を、判定可能な捕捉義務へ置き換えることにある。

実装:
1. §9.2のSemantic Resultスキーマに `mentioned_details: []` を追加する。Narratorに「今の描写で新しく出した名詞をここに列挙せよ」と要求する。**このフィールドは `narrative` より後に置く**（§I-7のフィールド順序と整合させるため。描写を書く前に「出した名詞」は列挙できない）。
2. `mentioned_details` は `provisional_detail` として同Turnにコミットする。検索対象には入るが、権威は低い。
3. プレイヤーが参照したら昇格する。既存Canonと矛盾するときだけ却下フローへ送る。
4. **`provisional_detail` の寿命は現在のシーン内に限る。** シーン終了時に昇格しなかったものは破棄する（Transcriptには残るので失われない）。これをやらないと、§V-2の「Canonをプロンプトへ入れる」方式で暫定詳細がプロンプト膨張の支配要因になる。

**この方式で解決しないこと（明記しておく）**: 列挙の網羅性そのものはモデル依存であり、決定論的には保証できない。ただし「網羅されたか」はNarrative本文と突き合わせて事後に測れるので、**指標として改善できる。** 禁止リストの遵守判定にはその経路がない。

### 併せて解消しておくべき衝突

§15.3 Economyモードは「**NPC ActorとNarratorを統合する**」と明記している。一方§9.3はNarratorに「**NPCが知る新情報**」の追加を禁じており、§8.1のNPC Actorはまさにそれを生成するのが責務である。**統合された1出力のどの部分に禁止が及ぶのかが決まっておらず、§20-9はEconomyモードでは構成上判定不能になる。**

捕捉義務方式に切り替えると、この衝突は自動的に消える。統合出力であっても「新しく出した情報を列挙する」という義務は同じ形で課せるため、ロールの統合と独立に成立する。

§14.3のContractへの追加案は §V-4 にまとめる。

## I-3. Recall GateはPull型のみで、GM自身の平常運転での捏造を防げない

### 何が問題か

§10.5のRecall Gateは、次のフローで始まる。

> Recall Queryを検出
>   ↓
> Canon / State / Transcriptを検索

**これは「プレイヤーが過去について質問したとき」しか守らない。**

しかし、一貫性の崩壊が実際に起きるのは、質問されたときではなく、**GMが通常の描写の中で過去の事実に再言及するとき**である。

- 「いつもの宿屋『金の鹿亭』に戻った」— Recall Queryではないが、宿屋の名前を誤記憶または捏造している
- 「先日助けた商人が声をかけてくる」— 商人を助けた事実の有無を検索していない
- 「あなたの持っている鍵では開かない」— 所持品を検索していない

§1が挙げる弱点「過去に決めた事実を、後からそれらしく捏造する」は、質問応答の場面より平常運転の場面で頻繁に発現する。Recall Gateはその大半を素通りさせる。

加えて、§20-2は「500Turn相当前に決めたNPC名」を目標に置いているが、**実際に興ざめするのは3〜10ターン前の忘却**である。ドアを開けた直後に「鍵のかかったドアがある」と描写する類。的が遠すぎる。

### どの状況で問題になるか

セッション中盤以降、常時。特にPrompt Cacheや要約でコンテキストを削った直後。

### Core Contractを変更すべきか

**具体化すべき。ただし「新設」ではない。**

公開前の検査は、原文に既に3箇所で規定されている。

- §7.2 Turn Engine の責務に「NarrativeとSemantic Resultの整合性確認」
- §21.5 秘密漏洩の対策に「Narrative Publish前の検査」
- §14.6 の Hook Point に `narration.before_publish`（Hook権限には `veto` がある）

**したがって欠けているのは条項ではなく、次の2つである。**

1. **検査の中身。** §7.2は検査対象を「NarrativeとSemantic Resultの整合性」と定めているが、**Canonとの照合**（過去に確定した事実との矛盾）は対象に含まれていない。Semantic Resultとの整合だけでは、そのTurnで新しく捏造された過去は検出できない。
2. **照合を成立させる前提。** 表層文字列からEntityを引く仕組みがないと、照合そのものが動かない（§I-9）。

§10.5のRecall Gate（Pull型）が7ステップのフローと6状態で詳細に定義されているのに対し、**Push型は責務の一行と対策の一行にとどまっている。** この非対称が問題であって、概念が無いわけではない。

### v0.1で対応すべきか

**対応すべき。ただし実装は軽い。**

### 推奨する修正案

**§7.2の「整合性確認」の対象に、Canonとの照合を明記し、その手順を定める。**

1. Canonの各Entityに、表記文字列とエイリアスの一覧を持たせる（「ガレス卿」「ガレス」「騎士ガレス」）。§10.2 L2の「必要な概念」にこれが無いので、追加する。
2. Narrative公開前に、生成テキストから既知Entityの表記を単純な文字列マッチで拾う。
3. 拾ったEntityについて、そのTurnで言及された属性がCanonと矛盾していないかを検査する。完全な意味検査でなくてよい。**まず効くのは「Canonに存在しない固有名詞が、既存のものであるかのように定冠詞的に言及されている」ケースの検出**である。
4. 矛盾を検出したら、Narrativeを1回だけ再生成する。2回目も矛盾したら、その旨をログに残して公開する（止めない）。

**Streamingとの関係**: この照合は完成したNarrativeを必要とするため、ストリーミング表示の前には完了できない。§I-7で述べるとおり、**検証を「公開前（構造化部分）」と「公開後（本文）」の2段に分ける**必要がある。公開後の照合で矛盾を検出した場合は、ロールバックではなく「GMが言い直す」形で訂正する。一人用プレイであれば許容できる挙動である。

これは§17.2の「正史矛盾数」を実際に測れる指標に変える。現状、この指標を算出する方法は文書に書かれていない。

**関連する必須の前提**: 表層文字列からEntity IDを引く仕組み（名寄せ）が文書に存在しない。これは §I-9 で扱う。名寄せがないと、この照合もRecall Gateも空振りする。

## I-4. 正史の権威が Event Log と Canon Ledger に二重化しており、境界が決まっていない

### 何が問題か

§23-4が自ら問うている論点だが、文書内では未解決である。

§4.2は両方を権威として置く。

> - append-onlyなイベントログを正しい履歴の基盤とする
> - Canon Ledgerを長期的な事実・決定の権威ある保存先とする
> - 現在状態はイベントとCanonから再構築可能なProjectionとする

一方、§20-1と§18 Phase 0の完了条件は、Eventのみを再構築元とする。

> §20-1: Event LogからAuthoritative Stateを再構築できる
> §18 Phase 0 完了条件: 状態をEventから再構築できる

§10.2 L3および§4.2は「EventとCanonから」としており、**同じ再構築の条件が2通り書かれている。**

さらに決定的なのは、§10.2 L1のEvent一覧に次が含まれることである。

> - CanonEstablished
> - CanonSuperseded

**Canonの変更それ自体がEventとして表現されている。** ならばCanon LedgerはEvent Logの Projection であり、State Projectionと同格の派生データである。にもかかわらず、§7.5では Event Store と Canon Store が並列に置かれ、§10.1では Canon が「権威ある記録」とされている。

### どの状況で問題になるか

実装の最初期。Canonの訂正（§10.7）を実装する段で必ず詰まる。「訂正Recordを追加する」とき、それはEventなのかCanonなのか。両方に書くなら、二重書き込みの整合性を誰が保証するのか。片方だけなら、もう片方はどう再構築されるのか。

また、§14.3-12「派生Indexを削除しても正史と状態を再構築できる」は、Canonが派生であれば自動的に満たされる。二重に永続化する限り、この条項は「二重書き込みが常に整合している」という追加の保証を要求することになる。

### Core Contractを変更すべきか

**整理すべき。** Contractの項目は変えなくてよいが、権威の順位を明記する必要がある。

### v0.1で対応すべきか

**対応すべき。** これはデータモデルの根幹であり、後から変えると全部作り直しになる。

### 推奨する修正案

**Event Store を唯一の真実の源（single source of truth）とし、Canon Ledger と State Projection を「どちらも Event からの Projection」として扱う。**

改訂案（§4.2および§10.1に反映）:

> - Event Log は唯一の権威ある永続記録である
> - Canon Ledger は Event Log から再構築される Projection である。Canonの成立・訂正・失効はすべて Event として記録される
> - State Projection も同様に Event Log から再構築される
> - Canon Ledger と State Projection は、削除しても Event Log から完全に再生成できなければならない

これにより:
- **§7.5の8ストアのうち、Canon Store / State Projection / Search Index が Projection に降格する。** 残る永続ストアは Event / Transcript / Versioned Content / **Secret** / **Telemetry** の5つ。
  - **Secret Store は降格できない。** APIキー保管であり、§14.3-9「APIキーはクライアント、通常ログ、モデルへ渡さない」に従えば append-only の Event Log には載せられない。鍵ローテーションも不可能になる。
  - **Telemetry Store も降格できない。** §II-10で述べるとおり、費用の記録はTurnのロールバックに追随してはならない。Eventの Projection にすると追随してしまう。
- §20-1と§10.2 L3の食い違いが消える（Eventのみが正しい）。
- §14.3-12が自動的に満たされる。
- §10.7の訂正が「訂正Eventをappendする」だけになり、二重書き込みの整合性問題が消える。

**予想される反論への回答**: 「Canonのbitemporal（Effective From/Until）やsupersedeチェーンはEventに載せにくい」— 載る。

```
CanonAsserted {
  canon_id,                 # ← 後述。決定論的に採番する
  subject, predicate, value,
  kind, holder, visibility,
  effective_from, effective_until,
  origin,                   # in_fiction | out_of_band ← §10.7 の区別
  source_transcript
}
CanonSuperseded { target_canon_id, reason, actor, origin }
```

Projection側でチェーンを畳めばよい。

**ただし、この案には満たすべき前提が2つある。**

1. **`canon_id` は決定論的に採番されなければならない。** Canonが純粋なProjectionであれば、再構築のたびに同じIDへ復元される必要がある。§10.5のEvidence ID、§14.3-6の「Recall回答には内部Evidenceが必要」、L0 Transcriptに記録済みの過去の回答根拠が、すべてこのIDを参照するためである。**採番はEvent ID（append順の連番）から導出する**のが最も安全。ランダムIDやDBのauto incrementを使うと、再構築でIDが変わってEvidenceが全部壊れる。
2. **`origin` フィールドが要る。** §10.7は「作中で新事実が判明したのか、卓外で設定を修正したのかを区別する」ことを求めている。イベントペイロードにこれを持たせないと、Projectionでは復元できない。

**個人開発としての効果**: 永続ストアが8から5に減り、Canonの二重書き込みの整合テストが不要になる。§0.2で「数ヶ月」に分類したCanon Ledgerの工数のうち、相当部分がここで消える。

## I-5. Canonの分類軸が3箇所に分散し、値が重複している

### 何が問題か

§10.4は「少なくとも以下を区別する」として次の13種を列挙する。

> - confirmed_fact
> - current_state
> - ruling
> - table_agreement
> - plan
> - promise
> - knowledge
> - belief
> - rumor
> - hypothesis
> - scenario_secret
> - disputed
> - superseded

**この列挙は単一のenumであるとは書かれていない。** そこは正確に読む必要がある。§10.2 L2の「必要な概念」には Epistemic Status / Visibility / Current Status が**それぞれ別のフィールドとして**並んでおり、§10.2 L4は世界の真実／PCの知識／NPCの信念／噂を**独立したレイヤーとして**扱っている。

**問題は、この13の値が、既に別フィールド・別レイヤーとして存在する軸と重複していることである。**

| §10.4 の値 | 実際にはどこの軸か | 重複先 |
|---|---|---|
| confirmed_fact, current_state, ruling, table_agreement, plan, promise, hypothesis | 命題の種類 | Epistemic Status本来の軸。これはよい |
| knowledge, belief, rumor | 認識主体 | **§10.2 L4** と重複 |
| scenario_secret | 可視範囲 | **§6.2 の「GM Runtimeのみ」** および L2 の Visibility と重複 |
| disputed, superseded | レコードの状態 | **L2 の Current Status** と重複 |

つまり同じ情報を2箇所で表現できてしまう。「シナリオ秘密」を `epistemic_status: scenario_secret` で表すのか `visibility: gm_only` で表すのか、文書からは決まらない。「NPCの信念」を Canon の値で表すのか L4 のレイヤーで表すのかも決まらない。

### どの状況で問題になるか

実装の最初のCanonレコードを書く瞬間。

「NPCのガレスは、王が北へ逃亡したと信じている」を保存しようとすると、次のどれを使うか決まらない。

- `epistemic_status: belief` で保存する（§10.4の値）
- `epistemic_status: confirmed_fact` + L4のNPC信念レイヤーへ保存する（ガレスがそう信じているという事実自体は確定している）
- L4のレイヤーにのみ保存し、Canonには置かない

**どれを選んでも動くが、選び方が決まっていないと検索が壊れる。** 「ガレスが信じていることを全部出せ」というクエリが、保存経路によってヒットしたりしなかったりする。Recall Gate（§10.5）は構造化検索を第1段に置くので、ここが揺れると第1段が空振りする。

§10.4の末尾の意図（「NPCの信念」と「世界の真実」を同じ値として扱わない）は正しい。**問題はその意図が3箇所に分散して実現されており、どれが正なのかが決まっていないこと。**

### Core Contractを変更すべきか

**Canonスキーマの整理。** §14.3-5「Canonには出典、時点、状態がある」に、軸を明示的に列挙する。

### v0.1で対応すべきか

**対応すべき。** 3軸への分解自体はコストが増えない（むしろ減る）。

### 推奨する修正案

**軸を1箇所に集約する。L4を独立レイヤーではなくCanonの `holder` フィールドとして統合し、§10.4の列挙から可視性とライフサイクル相当の値を除く。**

```yaml
kind:      fact | state | ruling | agreement | plan | promise | hypothesis
holder:    world | character:<id> | faction:<id> | rumor
status:    active | disputed | superseded
visibility: <§6.2の可視範囲>       # scenario_secret はここへ吸収
```

先の例:
```yaml
# 「ガレスは王が北へ逃亡したと信じている」
kind: fact
holder: character:gareth
status: active
subject: king
predicate: location
value: north
```
```yaml
# 「実際には王は死亡している」
kind: fact
holder: world
status: active
visibility: gm_only
subject: king
predicate: alive
value: false
```

同じ命題を holder 違いで並べられるようになり、§10.2 L4 が別レイヤーではなく Canon の1フィールドとして統合される。**記憶階層 L0〜L7 のうち L4 が1つ減る。**

**この整理で消える値**: `scenario_secret` → `visibility` へ。`superseded` / `disputed` → `status` へ。`knowledge` / `belief` / `rumor` → `holder` へ。残るのは命題の種類7値のみ。

**v0.1でのさらなる削減**: 最初は `kind` を fact / ruling の2値、`holder` を world / pc / npc:<id> の3系統、`status` を active / superseded の2値に絞ってよい。13の値をそのままenumとして実装しようとすると、必ず「これはどれか」で手が止まる。

## I-6. Turnに「プレイヤー待ち」の中断状態がなく、曖昧入力・二重送信・やり直しがすべて行き場を失う

### 何が問題か

§9.1の基本フローは、受信から公開まで一直線である。

> 1. Player Inputを受信 … 11. クライアントへ配信 … 12. Telemetryと検索用派生情報を更新

**途中で止まってプレイヤーへ問い返し、応答を待つ分岐がない。**

正確を期すと、§9.5には「止める」方向の記述は存在する。

> - ルール根拠が見つからない: 明示的なGM裁定として記録するか、**処理を止める**
> - 正史と矛盾: 自動上書きせず、**拒否**、曖昧化、訂正フローのいずれかへ送る
> - Narrative生成失敗: コミット前なら**Turn全体を保留**し、定型フォールバックを検討する

§14.6のHook権限にも `veto` があり、`state.rollback` もある。**したがって「止める」「拒否する」手段は存在する。**

**存在しないのは「止めたうえでプレイヤーへ問い返し、その応答を受けてTurnを再開する」経路である。** §9.5の3項目はいずれもTurnを終了させる方向で、再開の定義がない。

これにより、TRPGで頻繁に起きる次の状況に対応する手段が文書内に存在しない。

**(a) 曖昧な入力**
§8.1のInput Interpreterは「プレイヤー入力の対象、意図、曖昧さを整理する」とあり、§11.2のRuling要件にも「曖昧さ」「採用した解釈」があり、§13.2には `ambiguity_policy` がある。**つまり曖昧さを検出して記録する仕組みは想定されている。** しかしそれらはすべて「AIが解釈を選んで記録する」経路であり、**プレイヤーに選ばせる経路がない。** プレイヤーが「見張りをやり過ごす」と書いたとき、隠れるのか、買収するのか、走り抜けるのかで適用ルールもダイスも変わるが、Input Interpreterがどれか1つを選んでコミットする。

**(b) 判定前の選択**
「回避に運点を使うか」「どの技能で振るか」— TRPGで最も重要な選択が、常にAIの独断になる。これは§26の「選択に意味があり」に正面から反する。

**(c) 二重送信・リロード・タイムアウト後の再入力**
§6.3は「初期進行はサーバー側で直列化し、一つのTurnを完全に終了してから次の入力を処理する」とするが、処理中に届いた2件目の入力を待たせるのか捨てるのかが書かれていない。冪等性キー（Turn ID）の概念も文書内に存在しない。

**(d) やり直し**
§10.7「訂正とレトコン」は設定の誤りを後から直す手続きであり、**直前のTurnそのものを取り消す話ではない。** 一人用プレイでは、入力の意図がAIに誤解されて望まない行動が確定する事故が高頻度で起きる。文書にはUndo・振り直し・分岐セーブのいずれも記述がない。

**(e) 却下**
これは§9.5の「正史と矛盾: 拒否、曖昧化、訂正フローのいずれかへ送る」で部分的にカバーされている。**ただし「拒否」した後にプレイヤーが何をすればよいのかが定義されていない。** 「実はこのNPCは俺の兄だ」という宣言を拒否したとき、Turnは終わるのか、入力し直せるのか、その間の状態はどうなるのか。

### どの状況で問題になるか

(c) は具体的にこうなる。プレイヤーが「扉を蹴破る」と送信し、40秒待って不安になりリロードする。サーバーには進行中のTurnが残っており、リロード後の画面には何も表示されないため、同じ入力をもう一度送る。**同一行動でダイスが二度振られ、二度課金され、Event Logには扉が二回壊れた記録が残る。**

(a)(b)(d) はほぼ毎セッション。特にAI GMは「プレイヤーの意図を確認せずに進める」失敗を起こしやすく、これが「選択に意味がない」という体験上の最大の不満に直結する。

### Core Contractを変更すべきか

**変更すべき。** Turnモデルそのものの定義に関わる。

### v0.1で対応すべきか

**対応すべき。後から足すとTurn Engineとトランザクション境界の作り直しになる。**

### 推奨する修正案

**Turnに「awaiting_player」という中断状態を最初から入れる。**

```text
Turn状態: pending → running → awaiting_player → running → committed
                                     ↑              ↓
                                     └──────────────┘
                             (プレイヤー応答で再開、複数回可)
                    running → aborted (入力却下 / エラー / 予算超過)
```

この1つの機構で、上記(a)〜(e)がすべて同じ形で扱える。

- (a) 曖昧入力 → `awaiting_player` に入り、Semantic Resultの `clarification_request` を提示
- (b) 判定前の選択 → 同上。ダイスを振る前に中断してリソース使用を確認
- (c) 二重送信 → Turnに冪等性キーを持たせ、`running` 中の同一キーの再送は握り潰し、進行中である旨を返す
- (d) やり直し → `awaiting_player` で待っている間はまだコミットされていないため、そのまま `aborted` にできる。コミット後のUndoは別途必要だが、事故の大半はコミット前に防げる
- (e) 却下 → §9.5の「拒否」を `aborted` + 理由の提示として実装し、入力し直せる状態に戻す

**§9.2のSemantic Resultスキーマに追加するフィールド:**
```yaml
clarification_request:      # 空でなければ awaiting_player へ
  question: ""
  options: []
rejection:                  # 空でなければ aborted へ
  reason: ""
```

**§9.5のエラー一覧に、入力側の項目を追加する:**
> - 入力が曖昧: Turnを `awaiting_player` にし、選択肢とともに問い返す。状態は変更しない
> - 入力が世界設定と矛盾する / 物理的に不可能: Turnを `aborted` にし、理由を提示する。状態は変更しない
> - 処理中に同一Turnの再送を受信: 冪等性キーで判定し、握り潰して進行中である旨を返す

**(d)のコミット後Undoについて**: v0.1では「1ターンだけ戻せる」で十分。Event Logがappend-onlyなので、`TurnReverted { target_turn_id }` イベントをappendしてProjectionから除外する方式が最も安い。Canonの訂正Record（§10.7）を事故処理に流用すると、Canon Ledgerが訂正だらけになり、§20-4の「現在値と旧値を区別できる」機能が本来の目的（作中で新事実が判明した場合）に使えなくなる。**事故のUndoと作中の設定変更は、別の機構に分けるべきである。** §10.7にこの区別を明記することを推奨する。

## I-7. StreamingとTurnの原子性が衝突しており、どちらを取るかが決まっていない

### 何が問題か

§14.3-3はこう定める。

> 3. Turnの状態変更と公開は原子的に扱われる

§9.1のフローも同様。

> 10. Event、Canon、Transcript、表示を原子的にコミット
> 11. クライアントへ配信

一方、§7.3のAI Runtimeの責務には「構造化出力、Tool Calling、Streamingの扱い」があり、§15.1のCapability一覧にも「Streaming」がある。

**この2つは両立しない。** Narrativeをトークン単位で流し始めた時点で、コミットも検証も済んでいない。ここでValidatorが可視性違反や正史矛盾を検出しても、既に画面に出た数十文字を取り消す手段がない。

逆にStreamingを捨てると、Strict Path（§9.4）の重要ターンでは、複数回のモデル呼び出しの間、何も表示されない画面をプレイヤーが見続けることになる。

**そして§5.7は「費用と待ち時間は品質の一部である」と明言している。** 待ち時間の体感はStreamingの有無に強く依存するため、これは体験の中核に直結する判断だが、文書はこの衝突に触れていない。§23-9が「Turnの原子性とNarrative公開の順序が妥当か」とレビュー設問として挙げているのみである。

### どの状況で問題になるか

Strict Pathの重大ターン。裁定→世界更新→演出と3回呼ぶと、体感で30〜60秒。無表示でこの時間を待たされると、テンポが完全に死ぬ。

### Core Contractを変更すべきか

**§14.3-3の文言を精密化すべき。**

### v0.1で対応すべきか

**対応すべき。** 体感速度は「遊べるか」に直結する。

### 推奨する修正案

**検証を「公開前」と「公開後」の2段に分け、構造化出力のフィールド順序をそれに合わせる。**

```yaml
# 出力スキーマの順序（この順序が意味を持つ）
# --- ここまでを公開前に検証する ---
rulings: []
proposed_events: []
proposed_canon: []
knowledge_changes: []
visibility_changes: []
director_updates: []
clarification_request: {}   # I-6 で追加。空でなければここで中断
narrative_plan: []          # §9.2 に既存
# --- ここから公開（ストリーミング）---
narrative: ""
# --- ここからは公開後に処理する ---
mentioned_details: []       # I-2 で追加。描写を書く前には列挙できないので narrative の後
evidence: []
```

処理:

**第1段（公開前・ブロッキング）**
1. ストリームを受けながらJSONを逐次パースする
2. `narrative` の直前までが揃った時点で、**スキーマ検証・可視性検証・状態整合検証**を実行する
3. 検証に落ちたら `narrative` は1文字も表示せず、再生成または中断する

**第2段（公開・ストリーミング）**
4. 検証を通ったら、`narrative` の文字列を到着順にクライアントへ流す

**第3段（公開後・非ブロッキング）**
5. `mentioned_details` を `provisional_detail` としてコミットする（I-2）
6. **Narrative本文とCanonの照合**（I-3）を走らせる。矛盾を検出したら、ロールバックではなく訂正として次の表示に反映する

**なぜ2段に分けるのか**: I-8で挙げる検証3点のうち、「既知Entityとの照合」と「数値の一致」は**完成したNarrativeを必要とする**。これらを公開前に置くとStreamingできず、Streamingを取ると公開前には置けない。**両方を同時に満たすことはできないので、どちらを公開前に置くかを明示的に決める。** 状態を汚す可能性のある検証（可視性・状態整合）を公開前に、表示の正しさに関する検証（照合）を公開後に置く。

**この案が依存している前提と、その扱い（重要）**

- **JSONのキー生成順がスキーマ順に従うこと。** 多くのプロバイダの構造化出力では実際そうなるが、**これは仕様として保証されたものではない。** §15.1が複数Provider抽象化を前提にしている以上、正しさの根拠をここに置くべきではない。
  → **対策**: 順序が崩れた場合は自動的に非Streamingへフォールバックする（全体を受信してから検証・表示）。正しさは常に保たれ、体感速度だけが落ちる。§5.3の「プロンプトで頼むことと、コードで強制することを分ける」に沿う。
- **体感速度の改善幅は、構造化部分の長さに依存する。** `narrative` の1文字目までに、それ以前の全フィールドの生成が完了している必要がある。構造化部分が短ければ待ち時間の大半を削れるが、`director_updates` や `proposed_canon` が長いターンでは削減幅が小さくなる。
  → **対策**: Fast Pathでは `director_updates` を出さない（§I-8の推奨と同じ）。これで構造化部分が短く保たれる。

§14.3-3の改訂案:
> 3. Turnの状態変更と公開は原子的に扱われる。Narrativeのストリーミング表示は、状態変更に関わる構造化結果の検証が完了した後にのみ開始してよい。表示内容そのものの照合は公開後に行い、矛盾は訂正として反映する

## I-8. Fast Pathの検証手法が未定義で、ロール統合の上限も決まっていない

### 何が問題か

**(a) 検証の手法が定義されていない。**

§9.4のFast Pathはこう書かれている。

> - 一回のモデル呼び出しからSemantic ResultとNarrativeを得る
> - 構造化部分と文章を検証
> - 問題がなければ同時にコミット・公開する

検証**対象**は§7.2に書かれている（「NarrativeとSemantic Resultの整合性確認」）。**未定義なのは手法である。** Narrativeに書かれた事実がSemantic Resultに含まれているかを判定するには、Narrativeを解析して名詞と数値を抽出する必要があり、それは追加のモデル呼び出しかコードでの抽出になる。

**Fast Pathのコスト優位は「検証コストがゼロに近い」という前提に立っているが、その前提が検証されていない。** 検証を真面目にやるとFast PathがStrict Pathより高くなる可能性がある。**やらないことを明記しない限り、実装時にここで詰まる。**

**(b) ロール統合の上限が決まっていない。**

§8.2は「軽いTurnでは、複数ロールを一つのモデル呼び出しで処理してよい」とし、統合の例として「NPC Actor + Narratorを一回で処理」を挙げる。§15.3 Economyも「NPC ActorとNarratorを統合する」と明記する。**つまり文書が明示している統合はこの組み合わせだけである。**

一方§9.2のSemantic Resultには `director_updates` と `narrative` が同居しているが、これは「内部では、少なくとも次のような構造化結果を扱う」という**論理スキーマ**の記述であり、1回の呼び出しの出力とは書かれていない。

**問題は、どこまで統合してよいかの上限が定義されていないことである。** もし `director_updates` と `narrative` を1回で出すなら、§8.3が定めるDirectorのContext View（「シナリオ秘密、未解決ビート、手掛かり、クロック、プレイヤー傾向」）を渡した同じ呼び出しがプレイヤー向けNarrativeを生成することになり、§5.4が明示的に禁止した構図になる。

> 各ロールには、その責務に必要な最小限のContext Viewだけを渡す。NPC Actorへ世界の真相を渡してから「知らないふりをせよ」と依頼しない。

§8.2は「論理的な出力契約は、物理的な呼び出しを統合しても維持する」と書くが、これは**出力側**の契約である。**入力側のContext分離に対する上限**は書かれていない。§14.3-4「可視性確認前の情報をモデルへ渡さない」も、可視性を確認した上で秘密を渡すことは禁じていない。

### どの状況で問題になるか

(b)は秘密を含むシナリオ全般。統合の上限が書かれていないため、実装者は「1回で全部出す」ほうへ寄せる（そのほうが安いから）。すると§20-5「GM専用の真相をプレイヤー向けRecallで取得できない」はRecallの話として満たされていても、**Recallより先にNarrativeが漏らす。** §21.5（秘密漏洩）のリスクは正しく認識されているのに、その対策（RoleごとのContext View）が統合によって無効化される。

### Core Contractを変更すべきか

**§14.3-4を精密化すべき。**

### v0.1で対応すべきか

**対応すべき。ただし、v0.1では単純化で回避するのが正しい。**

### 推奨する修正案

**(a) 検証の中身を明記し、範囲を限定する。**

§9.4に追記:
> Fast Pathにおける検証は、決定論的に実行できる次の3点に限定する。§I-7の2段構成に従い、実行するタイミングも指定する。
>
> | # | 検証 | タイミング |
> |---|---|---|
> | 1 | 構造化出力のスキーマ適合 | 公開前（ブロッキング） |
> | 2 | 可視性・状態不変条件の検査 | 公開前（ブロッキング） |
> | 3 | Narrativeに含まれる既知Entityの表記と、Canonの矛盾照合（§I-3） | 公開後（訂正で対応） |
> | 4 | Narrativeに含まれる数値と、`proposed_events` の数値の一致 | 公開後（訂正で対応） |
>
> これを超える意味的整合の検証はFast Pathでは行わない。意味的整合が必要なTurnはStrict Pathへ回す。

曖昧に「検証」と書くと実装時に必ず破綻する。**やらないことと、いつやるかを明記するほうが安全。**

**(b) 統合の上限をContractとして明記する。**

§14.3への追加案:
> 4b. 単一のモデル呼び出しに、公開向け出力の生成と、その公開先に不可視な情報の参照を同時に含めてはならない

**これは新しい方針ではなく、§15.3 Economyモードが既に採っている方針をContractへ格上げするものである。**

§15.3 Economy の記述:
> - Directorはシーン境界または異常時
> - NPC ActorとNarratorを統合する

つまり文書自身が「Directorは毎ターンの統合呼び出しに入れない」と書いている。**それをEconomyモードのローカルな設定ではなく、全モード共通の不変条件にする。**

**v0.1での実装**: Fast Pathから `director_updates` を外し、Directorはシーン境界でのみ別の呼び出しで動かす。これでFast Pathの入力から秘密が消え、§I-7で述べた「構造化部分を短く保つ」要件も同時に満たせる。追加コストはほぼゼロ。

**さらにv0.1では**: Turn Planner（§8.1-2）を作らず、**全ターンFast Path固定**にすることを推奨する。理由は §V-2 に書く。Turn Plannerは自由文から「危険度」を判定する分類器であり、決定論的ルールでは書けず、分類誤りのコストが高い（重大ターンをFast Pathに流すと不整合が出る）。1本を安定させてから分岐を足すほうが安い。

## I-9. 表層文字列からEntity IDを引く仕組み（名寄せ）がなく、日本語運用の前提も抜けている

### 何が問題か

**(a) 名寄せが存在しない。**

§10.6の検索順序は、第1段からIDが既知である前提で書かれている。

> 1. Entity ID、Predicate、Kind、時点、可視性による構造化検索

§10.2 L2にも「安定したEntity ID」がある。

**関連する記述は分散して存在する。** §8.1のInput Interpreterは「プレイヤー入力の**対象**、意図、曖昧さを整理する」を責務に持ち、§10.6の第2〜4段（全文検索、ベクトル検索、Transcript原文検索）はID未知時の経路として読める。§10.5には `ambiguous` 状態がある。

**欠けているのは2つ。**

1. **エイリアスの保持先。** §10.2 L2の「必要な概念」に表記ゆれ・別名を保持するフィールドがない。保持先がなければ、どの経路で引いても照合先が作れない
2. **工程としての位置づけ。** 名寄せがInput Interpreter・§10.6の下位段・`ambiguous` 状態に分散しており、「まず名寄せを行い、失敗したら問い返す」という手順として定義されていない

Canonに `npc:gareth`（表記「ガレス卿」）で登録されているNPCを、プレイヤーは「ガレス」「がれす」「あの騎士」「さっきの人」「Gareth」と呼ぶ。エイリアスがないため第1段の構造化検索は空振りし、第2段（全文検索）も後述(b)の理由で日本語では機能しない。結果としてベクトル検索だけが残る。

**§20-2（500Turn前のNPC名をEvidence付きで回答できる）は、開発者がIDを直接指定するテストでは通り、実プレイでは通らない。** 最も危険な種類のバグである。

**(b) 日本語の全文検索が素朴な選択では機能しない。**

§10.6の第2段は「全文検索」である。しかし日本語は空白で語が区切られない。SQLiteのFTS5をデフォルトのunicode61トークナイザで使うと、CJK文字の連続が1トークンとして扱われ、部分一致がほぼ効かない。PostgreSQLの `to_tsvector` も同様に、日本語用の設定なしでは機能しない。

対策は形態素解析（MeCab / Lindera / Sudachi）かN-gram索引（FTS5のtrigramトークナイザ、pg_bigm、PGroonga）のいずれかで、**これは§4.3「データベースと検索基盤」の選定を強く縛る。** 文書はこれを言語非依存の未決事項として扱っている。

この故障は静かに起きる。第2段が常時0件を返し、第1段（名寄せがないので空振り）と合わせて、**ベクトル検索だけが残る。** すると§10.6の原則が破れる。

> ベクトル検索は候補発見に使い、正史の判定根拠にはしない。

しかも、テストを英語のダミーデータで書いていると最後まで検出されない。

**(c) トークン量の前提**

§5.7は「入力トークン、出力トークン」を設計対象とするが、言語による差に言及がない。多くのトークナイザで日本語は英語より1文字あたりのトークン消費が大きく、同じ内容を表すのに必要なトークン数が増えやすい。Ruleset Core、GM Policy、Scenario Segment、Canon Evidenceがすべて日本語であれば、安定領域だけでプロンプトがかなりの量になる。桁が変わるほどではないが、英語想定の見積もりをそのまま使うと外れる。§15.4の予算設計は、実測値を取ってから決めるべきである。

**(d) NPCの口調がデータとして保存されない**

§8.1のNPC Actorに「口調」の語が1回あるだけで、§10.2 L2のCanon要素にも§10.3のCanon化対象にも口調は含まれない。§17.2の自動評価にも口調の指標がない。

日本語では一人称と語尾がキャラクター同一性のほぼすべてを担う。モデルを変えた翌セッションで、老練な傭兵が「〜だぜ」から「〜ですね」になると、名前とHPが保たれていてもプレイヤーには別人が出てきたようにしか見えない。§26の「NPCが自分の知識と目的に基づいて行動すること」は満たされているのに、体験としては破綻する。

### どの状況で問題になるか

(a)(b) はセッション開始から常時。(c) は予算設計の段階。(d) はモデル変更時とセッションをまたいだとき。

### Core Contractを変更すべきか

不要。実装仕様の問題。ただし§24の「2. Canon and Recall Specification」に名寄せを明記すべき。

### v0.1で対応すべきか

(a) は**必須**。(b) は**必須**（検索基盤の選定を縛るため）。(c) は実測で足りる。(d) は**安いので入れるべき**。

### 推奨する修正案

**(a) Entityに表記エイリアスの配列を持たせ、入力の名寄せを明示的な工程にする。**

```yaml
entity:
  id: npc:gareth
  canonical: ガレス卿
  aliases: [ガレス, がれす, 騎士ガレス, Gareth]
  kind: npc
```

- Canon確立時に、モデルに「この名前の別表記を列挙せよ」と出力させて自動登録する（追加呼び出し不要、Semantic Resultのフィールドで済む）
- 入力の名寄せは、まず単純な文字列一致・部分一致で引く。ヒットしなければベクトル検索で候補を出し、**曖昧なら I-6 の `awaiting_player` で問い返す。** これが名寄せ問題の最も安い正解。
- §10.5のRecall Gateのフローの先頭に「表層文字列→Entity ID解決」を工程として追加する。`ambiguous` 状態は既に定義されているので、失敗時の接続先はある

**(b) §4.3の未決事項に、日本語の制約を明記する。**

> - データベースと検索基盤（**日本語の全文検索には形態素解析またはN-gram索引が必須であり、選定はこの制約を満たすものに限る。素朴なFTS設定では日本語が分割されず、検索が静かに機能停止する**）

そして**テストデータは必ず日本語で作る**ことを§17.4のBenchmark Scenarioの要件に入れる。

**(c) §15.4の予算設計は、Phase 0で実測してから数値を決める。** 計画段階で数値を置かない。

**(d) NPCの口調をCanonに載せる。**

```yaml
kind: fact
holder: world
subject: npc:gareth
predicate: speech_style
value: "一人称は『儂』。語尾は『〜じゃ』。相手を『お主』と呼ぶ。丁寧語は使わない"
visibility: gm_runtime
```

Canonに載れば、§20-8「Model Providerを変更しても確定済みCanonは変わらない」の保護対象に自動的に入る。追加コストはほぼゼロで、体験への効果が大きい。§17.2に「NPC口調の逸脱数」を指標として足してもよい。

## I-10. プレイヤーキャラクターの作成と、シナリオ執筆のコストが、計画に存在しない

### 何が問題か

**(a) キャラクター作成がない。**

§6.1はCharacterを「プレイヤーまたはAIが操作するゲーム内存在」と定義するが、**その初期状態をどう生成するかが、ドメインモデルにもPhase計画にもv0.1範囲にも存在しない。** §11.4のReference Rulesetは「通常判定／対抗判定／ダメージ／状態／リソース／クロック／調査手掛かり／NPC関係／簡易戦闘」のみで、能力値・技能・作成手順への言及がない。

§10.2 L3のState Projectionは「現在HP」を持つが、そのHPの初期値をどこから得るのかが定義されていない。**最初のTurnを開始できない。**

結果として、実装者は場当たりにJSONを手書きすることになり、その形式が事実上の非公式仕様として固定される。

**(b) シナリオ執筆のコストが見積もられていない。**

§18 Phase 1の成果物に「一つの完成した検証Scenario」がある。これは§12.1の構造を持つ。

§12.1 のツリーを1行に潰すと、必要な記述量が見える。

`Scenario` = World Invariants / Secrets / Actors(Goals, Knowledge, Resources, Clocks) / Locations / Clues(Meaning, Access Paths, Reveal Conditions) / Narrative Beats(Prerequisites, Optional Dependencies, Consequences) / Failure States / Recovery Strategies / End Conditions

**これは実装ではなく執筆であり、自動化も外注もできない。** 手掛かりごとにMeaning/Access Paths/Reveal Conditionsまで、NPCごとにGoals/Knowledge/Resources/Clocksまで手書きすると、相当な分量になる。しかも編集UI（§4.3で未決）もバリデータもない。

**Phase 1の完了条件「シナリオを最後まで遊べる」は、Runtimeではなくシナリオ執筆でブロックされる可能性が高い。** そして§18 Phase 4に「Scenario / Rulesetの制作支援」が置かれており、支援ツールは最後まで来ない。

**(c) セッションの終わりと、次への引き継ぎがない。**

ログ閲覧面そのものは設計されている。§7のクライアント構成は「Chat / Character / Ruling / **Log** / Admin」であり、§16.1のデータフローも「Browser ← Result / State / **Log**」、§16.3にも「ログとエラー確認」がある。

**欠けているのは、セッションの区切りの扱いである。**

- §6.1はCampaignを「複数セッションにまたがる」単位と定義するが、**2回目のセッションが何から始まるかが書かれていない**
- 終了条件を満たしたことをEventとして記録する仕組みがない（§10.2 L1の例にも該当するものがない）。終了したことが状態として残らない
- §10.2 L5のEpisodic Summaryは「シーンやセッションの要約」として定義されているが、**それをいつ生成し、いつ表示するかが書かれていない。** 概念はあるが、使いどころが決まっていない

### どの状況で問題になるか

(a) はPhase 0の最初のTurnを実行する瞬間。(b) はPhase 1の直前。(c) は初回セッション終了時、および2回目の開始時。

### Core Contractを変更すべきか

不要。

### v0.1で対応すべきか

(a)(b) は**必須**。(c) は**セーブから再開する以上、事実上必須**。

### 推奨する修正案

v0.1では、キャラクター作成UIを作らない。**YAML 1ファイルを手書きする**でよい。ただし、その形式を§24の「1. Core Domain and Event Model」で先に決める。場当たりに決めると後で全部書き直しになる。

- 終了条件 2（成功／失敗）

Failure States と Recovery Strategies と Optional Dependencies は、**最初のシナリオでは書かない。** §12.3のDirector介入で代替する。

そして**パーサもエディタもバリデータも作らない。** YAML 1ファイルを直接読む。

**§18の成果物に「シナリオ執筆」を独立した作業項目として明記する。** 現状は成果物リストの1行に埋もれており、実装工数と同列に見える。

**(c) セッション終了時の成果物を定義する。**

- 終了条件を満たしたことをEventとして記録し、明示的に提示する（`SessionEnded { outcome }`）
- **「前回までのあらすじ」の生成と表示**。これは§10.2 L5（Episodic Summary）の最も実用的な用途であり、再生成可能な派生データとして既に定義されている。次のセッション開始時に表示する

## II-1. Runtime Contractを強制する手段が存在しない 【v0.1で文言修正】

§14.1はこう宣言する。

> すべての実装は交換可能になり得る。
> ただし、NeontoF Runtime Contractを破る実装は起動できない。

しかし§14.7は、v0.1のプラグインを信頼済みサーバーコードとして扱う。

> v0.1では、管理者が導入したコードプラグインを信頼済みサーバーコードとして扱う。

信頼済みコードとして実行する以上、プラグインは可視性フィルタや原子的コミットを単に呼ばないことができ、ランタイムはそれを検知できない。文書中で起動時に検査するとされているのは§14.4の「Capability Graphを検証し、不足、循環依存、互換性不一致をセッション開始前に検出する」だけで、これは能力の整合性検査であって、§14.3の12項目の遵守検査ではない。

**「起動できない」は、判定手続きが文書内に存在しない規範である。**

**修正案**: §14.1を次に変える。
> ただし、NeontoF Runtime Contractを破る実装は、正式なプラグインとして扱わない。v0.1では機械的な強制は行わず、Contract遵守はテストスイートによって検証する。

そのうえで、§14.3の12項目それぞれに対応するテストを§17.4のBenchmarkへ入れる。**強制できないなら、テストで検出する。** 文書上「起動できない」と書いてあると、実装時にその機構を作ろうとして時間を溶かす。

## II-2. 契約を守らせる主体自身が「交換可能な実装」に含まれている 【v0.1で文言修正】

§14.2の交換可能リストには次が含まれる。

> Prompt / Context Compiler、Turn Orchestrator、Event / Canon / Index Storage

一方、可視性を確定する主体は Context Compiler である。

> §6.2: Context Compilerは、モデル呼び出しの前に可視性を確定し、許可されない情報をプロンプトから除外する。

§5.9は「可視性、状態更新、リプレイ可能性などの契約はプラグインによって無効化できない」とするが、**可視性を確定する主体が差し替え可能なら、契約は差し替えによって消える。** 原子性（§14.3-3）とTurn Orchestrator、再構築可能性（§14.3-12）とStorageも同じ構造。

**修正案**: §14.2を「交換可能な実装」と「Core固定（交換不能）」に分ける。

| Core固定 | 交換可能 |
|---|---|
| Visibility Filter（可視性の確定） | Context Compiler の**組み立て方**（何を選んで入れるか） |
| Transaction Boundary（コミット境界） | Turn Orchestrator の**判断ロジック**（何を呼ぶか） |
| Event Store の append と読み出し | Canon / Index の**構築方法** |

つまり **「契約を守らせる薄い層」をCoreに固定し、その上の判断をプラグイン化する。** 現状の分割線は、守らせる層ごとプラグイン側に置いてしまっている。

**さらに深い問題: ストア横断の原子性をどう保証するのか。**

§14.3-3は「Turnの状態変更と公開は原子的に扱われる」とするが、§7.5は「物理的に同じデータベースへ実装してもよい」と述べるだけで、**同一DBを要求していない。** かつ§14.2は「Event / Canon / Index Storage」を交換可能実装に含めている。異なるバックエンドのプラグインを組み合わせた場合、複数ストアにまたがるコミットの原子性を保証する手段が文書内にない（分散トランザクションか、それに代わる仕組みが要る）。

**v0.1での修正案**: I-4の提案（Event Storeを唯一の権威とし、CanonとStateをProjectionにする）を採ると、**この問題が構造的に消える。** 原子的にコミットする対象がEvent Storeへのappend 1回だけになり、Projectionの更新は失敗しても再構築できるからである。§7.5に「Event Storeへのコミットは単一のトランザクション境界で行われなければならない。他のストアはすべてその後段の派生更新である」と明記することを推奨する。

## II-5. 同名の別概念が2組ある 【v0.1で用語整理】

**(a) Hard Constraint**

> §12.2: **Hard Constraint**: 絶対に破ってはいけない事実
> §13.4: 避けたいテーマ、表現の上限、セッション中断条件などは、好みのスライダーではなくHard Constraintとして扱う。

前者はシナリオ側が守らせたい世界事実、後者はプレイヤー側が禁じたい表現であり、方向が逆である。シナリオの不可侵事実が安全設定で禁じられたテーマに触れる場合、どちらも「絶対」なので解決できない。§14.5のマージ規則は「禁止事項: union」としか書かれておらず、どちらが優先するかがどこにも書かれていない。

**修正案**: 後者を `Safety Constraint` に改名し、**Safety Constraint が常に Hard Constraint に優先する**と明記する。優先順位を書かない安全設定は安全設定として機能しない。

**(b) Capability**

**プラグインの能力として**（§14.4 の Plugin Manifest 宣言項目）:
> - Provided Capabilities
> - Required Capabilities

**モデルの能力として**（§15.1）:
> Role Runtimeは特定モデル名ではなく、必要なCapabilityを要求する。

前者はプラグイン依存解決と権限付与の単位、後者はモデルルーティングの選定条件で、検証タイミングも失敗時の挙動も異なる。§14.5の「Capability: 明示付与またはintersection」がどちらに適用されるのかが一意に読めない。§25の「Capability Seam」も、どちらを指すか特定できない。

**修正案**: 後者を `Model Capability` に改名する。

## II-6. rescue_bias と §26 の北極星が衝突している 【方針の明確化】

§13.2 Challenge に `rescue_bias` があり、§13.3のプレイヤー向け設定に「厳しさ: 安心 / 標準 / 過酷」がある。

一方、§26はこう書く。

> ルールに従った結果が、演出の都合で消されないこと。

そして§1はLLMの弱点として「プレイヤーへ迎合し、失敗や不利益を無効化する」を挙げ、§5.3は「HP、所持品、ダイス…はコードで強制する」としている。

**`rescue_bias` と「安心」プリセットは、その迎合を設定可能なパラメータとして正面から導入するものである。** どこまで干渉してよいかの境界が定義されていない。§13.2の計測可能化の例4つ（`clue_redundancy`, `director_intervention_budget`, `target_turns_per_scene`, `fail_forward_strength`）に `rescue_bias` は含まれておらず、接続先が示されていない。

**修正案**: `rescue_bias` の作用範囲を明示的に限定する。

> `rescue_bias` は、ダイス結果、HP、資源の数値には一切干渉しない。作用するのは次に限る。
> - 失敗の帰結として提示される選択肢の数（脱出経路の提示）
> - NPCによる救援がシナリオ上妥当な場合に、それを発生させる確率
> - 致命的結果の前に警告を挟むか否か
>
> ダイスの目や適用ルールを変更することはできない。

これで§26と両立し、かつ `fail_forward_strength` との役割分担も明確になる。

## II-8. Recall Gate の `forbidden` の応答仕様がない 【v0.1で定義】

§10.5は6状態（found / not_found / ambiguous / conflicting / superseded / forbidden）を定義するが、応答仕様が書かれているのは `not_found` と `superseded` の2つだけである。

`forbidden` については次のようにある。

> `forbidden`の場合は、プレイヤーまたはキャラクターが知らない情報として扱い、検索結果自体を回答モデルへ渡さない。

しかし§14.3-6は「Recall回答には内部Evidenceが必要である」と定める。Evidenceを渡さない以上、この条項を満たす回答は生成できない。

さらに、`forbidden` の応答が `not_found` と同じ「未決定」なら、§20-3との区別がつかない。逆に別の応答を返せば、**「そこに秘密がある」という事実自体が漏れる。**

**修正案**: `forbidden` は `not_found` と**外形的に区別できない応答を返す**と明記する。これはセキュリティの一般則（存在の秘匿）と同じ考え方。§14.3-6には「ただし可視性により参照が禁じられた場合を除く」の但し書きを足す。

`ambiguous` と `conflicting` の応答仕様も未定義。前者は I-6 の `awaiting_player` へ繋げる。後者は「記録が食い違っている」ことをGMが明示し、訂正フロー（§10.7）へ送る。

## II-9. Transcriptを原子的コミットに含めると、失敗Turnの記録が残らない 【境界の明記】

> §9.1-10: Event、Canon、Transcript、表示を原子的にコミット
> §21.2 対策: Transcriptを最終監査記録として残す
§10.2 L0 が保持対象として列挙するもの（抜粋）:
> - Tool Callと結果
> - ダイス
> - エラー
> - 訂正
> - 表示内容

§20-12「API失敗時にTurnが部分コミットされない」と§9.5「API Timeout: 状態を変更せず、再試行可能な状態にする」に従えば、失敗したTurnはロールバックされる。Transcriptがその境界の内側にあるなら、**失敗したモデル呼び出しとエラーの記録も一緒に消える。** L0が列挙する「エラー」を保持できない。

**修正案**: Transcriptをトランザクション境界の外に出し、§9.1-10を次に変える。
> 10. Event、Canon、表示を原子的にコミットする。Transcriptはトランザクション外にappendされ、失敗したTurnの記録も保持される

Transcriptは「実際に送受信・表示された内容の原記録」（§10.1）なのだから、ゲーム状態のトランザクションとは別の寿命を持つのが自然。

## II-10. 費用はロールバックできないという非対称性が扱われていない 【v0.1で記録先を決める】

§14.3-10は「モデル呼び出し前に予算を検査する」とするが、実消費は呼び出し後にしか分からない。

Strict Pathで2回呼んだ直後にNarrator呼び出しがタイムアウトし、§9.5に従ってTurn全体が破棄されると、**ゲーム状態は正しく巻き戻るが、支払った2回分の費用は戻らない。** この消費がTurnのトランザクションと一緒にロールバックされる実装だと、Telemetryの合計とプロバイダの請求額が恒常的にずれ、§16.3の「使用量一覧」が信用できなくなる。

また、事前検査を通した1回の呼び出しが想定を大きく超えて出力することがあり、**上限は常に1回分オーバーシュートする。**

**修正案**: II-9と同じく、**Telemetryをトランザクション境界の外に出す。** そのうえで§15.4に追記する。
> 予算検査は事前に行うが、実消費は事後にしか確定しない。したがって上限は常に1回の呼び出し分だけ超過し得る。上限値はこの超過を織り込んで設定する。消費の記録はTurnのロールバックに追随しない。

## II-11. GM Policyの「例」と、v0.1の実装対象の対応が取られていない 【対応表を作る】

§13.2は Agency 5 + Challenge 6 + Pacing 5 + Narrative 6 + Referee 5 + NPC 5 = **32個**のパラメータを列挙する。

**まず正確に読むと、この節の見出しは「内部GM Policyの**例**」であり、§19のv0.1範囲も「**基本的な**GM Policy」に限定されている。** したがって32個を実装対象と読むのは誤読である。

**問題は、その「基本的な」が何を指すのかが、どこにも書かれていないこと。** §13.2の末尾はこう書く。

> 各パラメータは、可能な限り計測可能な処理へ接続する。

接続先が例示されているのは4つ（`clue_redundancy`, `director_intervention_budget`, `target_turns_per_scene`, `fail_forward_strength`）。うち `clue_redundancy` は32個のリストに載っていないので、**32個のうち接続先が示されているのは3個、残り29個は未定。**

例示のリストと実装対象の区別がつかない状態で32個が並んでいると、実装者はそこへ引きずられる。§0.2で述べた「最小実装の定義がない」のと同じ構造である。

**プロンプトに32個の数値を入れても、モデルは数個しか区別しない。** そして効果を検証する手段がない（§17.4のBenchmarkで32次元を測るのは非現実的）。

**修正案**: §13.2に**「v0.1で実装する」列を追加する。** 例示リストを消す必要はない。実装対象がどれかを表で明示すれば、誤読の余地が消える。

v0.1で実装するのは、§13.3のプレイヤー向け7設定が**直接指すものだけ**に限る。

| プレイヤー向け設定 | 接続先の実装 |
|---|---|
| 進行方針 | 選択肢サジェストの数、Director介入の上限回数 |
| 厳しさ | 目標値の補正、資源消費量、`rescue_bias`（II-6の限定範囲） |
| ルール運用 | 裁定時にルール参照を必須とするか |
| テンポ | 1シーンの目安ターン数 |
| 文章量 | GM応答の文字数上限 |
| 情報提示 | 手掛かり提示の明示度、`clue_redundancy` |
| 裁定透明性 | ダイス目・目標値・根拠の表示レベル |

**7設定 → 10個以下の内部値**。これで§13.1「面白さを単一値にしない」の趣旨は満たされ、実装量は1/3以下になる。

## II-12. ルールセットの必要数が節ごとに食い違っている 【文言修正】

> §11.4: その後、性質の異なる二つ以上の公開可能なルールセットを実装し、抽象化が特定システムに偏っていないことを確認する。
> §18 Phase 2 成果: 二つ目のRuleset

## II-13. Prompt Injection対策が対策の名前だけ 【v0.1では脅威モデルを明記して縮小】

§16.4の「必要な対策」の先頭は「Prompt Injection対策」である。これは対策の名前であって対策ではない。

ただし、位置づけが「個人開発・自分が遊びたい」であれば、**プレイヤー入力もシナリオもルール文書もすべて自分が書く**ため、脅威モデルは実質的に空である。§20-17, #18を厳密な受け入れ条件として扱う動機は薄い。

**一方、LLM出力そのものは非信頼データであり、これは自分1人でも変わらない。** §16.4の「信頼しない」リストにLLM出力と自動生成されたSummaryが入っているのは正しい。

**v0.1で実際にやる価値がある対策は次の2点。どちらも安い。**

1. **非信頼テキストを含むContext Viewを持つRoleには、状態変更能力のあるToolを渡さない。** Narrator と NPC Actor はTool無しにする。状態変更はSemantic Resultのスキーマ経由のみ（§9.2で既に方針は正しい）。
2. **Validatorには非信頼入力を見せない。** 検証対象と不変条件だけを渡す（§8.3で既にそう書かれている）。

**修正案**: §16.4の「Prompt Injection対策」を上記2点に具体化する。残り（Rate Limit、入力サイズ制限、アップロード検証、CSRF）は、公開する段階まで先送りしてよいことを明記する。

## II-14. 時間経過・移動・Scene境界が定義されていない 【v0.1で最小限を決める】

**(a) 時間と移動**

§10.2 L3のState Projectionに「時刻」「位置」、L1のEvent例に `CharacterMoved` と `ClockAdvanced` がある（L1は「**例:**」と明記されているので、網羅リストではない）。

**問題はEvent名の有無ではなく、規則が定義されていないことである。** 1Turnが何分・何時間に相当するかを誰が決めるのかが書かれておらず、§12.2の Clock も「時間や行動で進行する」とあって、どちらなのかが決まっていない。

プレイヤーが「隣町まで行く」と書いたとき、1Turnで完結するのか、途中で遭遇判定が入るのか、到着時刻をいくつにするのかを決める規則がない。World Simulatorが毎回違う答えを出すため、「日没までに戻る」という約束をCanonに保存しても、**日没が来たかどうかを誰も判定できない。**

**修正案（v0.1の最小形）**: 時間を実時刻で持たず、**クロックの目盛りだけで持つ**。「1シーン＝クロック1目盛り」と決め打つ。移動は「同一シーン内」か「シーン移動＝1目盛り消費」の2択にする。実時刻（何時何分）は描写の飾りとして扱い、判定には使わない。これで「日没までに」は「クロックがN目盛りに達するまでに」に翻訳でき、決定論的に判定できる。

**(b) Scene境界**

§6.1はSceneを定義し、§13.2に `target_turns_per_scene` があり、§8.1のDirectorに「シーン進行」がある。しかし**誰がいつSceneを開始・終了させるのかが定義されていない。** L1のEvent例にもSceneの開始・終了に相当するものがなく（L1は例示なので不在自体は根拠にならないが）、§14.6のHook Pointにも `scene.*` がない。**Hook Pointは22点が列挙された網羅的なリストなので、こちらの不在は意味を持つ。**

プレイヤーが宿屋での会話を続けているのに、Directorが `target_turns_per_scene` 到達を理由に「翌朝、あなたは目を覚ます」と場面を切ると、時間が進んだことがCanonに記録されているのか単なる描写なのかも判別できない。§14.6のフックもEpisodic Summaryの生成タイミングも掴めない。

**修正案**: `SceneStarted` / `SceneEnded` をEventに追加する。Scene遷移はプレイヤーの明示的な合意を要する（I-6の `awaiting_player` を使う）か、明確な移動・時間経過の宣言によってのみ起きる、と定める。**Directorがターン数だけを理由に場面を切ることは禁止する。**

## II-15. 単一Seedでは §17.4 の「構成を変えて再生」が成立しない 【v0.1で導出規則を決める】

3つの要求が同時には満たせない。

> §17.1: 決定論的なRule、Dice、State Projectionは再現可能であるべきである
> §20-11: ダイス結果はSeedとともに監査できる
> §17.4: 同じ初期状態と入力列を、異なるモデル、GM Policy、Memory、Orchestratorで再生できる検証シナリオを用意する

**ダイスを振る回数と順序は、モデルが提案する行為に依存する。** セッション単位の単一Seedストリームから順に消費する実装だと、モデルやGM Policyを変えた瞬間に消費回数がずれ、以降の乱数列が全部変わる。「モデルAでは成功したがモデルBでは失敗した」のが判断の差なのか乱数のずれなのかを区別できず、§17.4の比較が成立しない。

**修正案**: **呼び出しごとにSeedを導出する。**

```
seed = H(campaign_seed, turn_id, action_id, roll_index)
```

`turn_id` はTurnの連番、`action_id` はそのTurnで判定を要した行為の識別子、`roll_index` は同一行為内での連番。これなら、同じ行為に対しては構成を変えても同じ目が出る。構成の違いによって行為そのものが変われば目は変わるが、それは測りたい差分そのものなので問題ない。

§17.1と§20-11の「Seedとともに監査」も、導出に使った4つの値を記録すれば満たせる。実装は数行。**ただし後から変えると過去のReplayが全部無効になるので、最初に決める必要がある。**

> ### 3.2 第一の提供形態

### ただし、この3点だけは最初から守る

複数人対応のデータモデルを全部前払いする必要はないが、**コストがほぼゼロで、後の書き直し量を大幅に減らす**規律が3つある。§20-20（反証不可能な条件）は、これに置き換えるとよい。

3. **状態を直接書き換えず、必ずEventをappendしてからProjectionを再計算する。** これがEvent Sourcingの本質であり、最も安く、最も効く

**§20-20を次に置き換える。**
> 20. すべてのエンティティが安定IDで参照され、すべての事実が可視範囲を持ち、すべての状態変更がEventのappendを経由している

### #3 について（ここを雑にやると秘密が漏れる）

「Canon全件をプロンプトに入れる」と単純に書くと、**Canonには定義上GM専用情報が含まれるため**（§10.3のCanon化対象に「シナリオ上の秘密」、§10.4に `scenario_secret`、§6.2に「GM Runtimeのみ」）、プレイヤー向けNarrativeを生成する呼び出しに秘密を渡すことになる。これは§5.4・§8.3を破り、§20-5が成立しなくなる。**本レビューがI-8で批判し、V-4で契約4bとして禁じた構図そのものである。**

したがって、正確には次のようにする。

1. **投入するのは、そのTurnの公開先から見て可視なCanonのみ。** `visibility` でフィルタする。これは可視性フィールドが最初からあれば単純なWHERE句で済む（V-1の規律2が効くところ）
2. **GM専用情報は、シーンの開示条件を満たしたものだけを追加投入する。** v0.1のシナリオは秘密を1つに絞る（§I-10の推奨）ので、GM専用Canonの量は数件で済む。開示条件の判定はコードで書ける
3. **各Canonに短いID（`c17` のような連番）を付けてプロンプトへ入れる。** 過去の事実に言及する際は、そのIDを `evidence` フィールドに列挙するようモデルへ要求する
4. **`evidence` に挙がったIDが実在し、かつ公開先から可視であることをコードで検証する。** 実在しないIDを挙げたら再生成する

**4がRecall Gateの中核（§14.3-6「Recall回答には内部Evidenceが必要である」）を、検索基盤なしで満たす。** 検索が要らないのは「全部見えているから」であって、Evidenceの要求まで消えるわけではない。ここを省くと、§1が挙げた「過去に決めた事実を、後からそれらしく捏造する」がそのまま復活する。**I-3で指摘した問題（GMは平常運転で捏造する）は、データが目の前にあっても起きる。**

なお、これでも `provisional_detail`（§I-2）は現在シーン内のものだけを投入する。全部積むとプロンプト膨張の支配要因になる。

## V-3. Phase順序の改訂案

### 現行順序の評価

**方向は正しい。** Web UIより先にターン・状態・記憶の意味論を検証する（Phase 0）という判断は妥当で、UIから作ると状態設計が引きずられる。

**問題は4点。**

1. Phase 0の中身が重すぎる（Canon Ledger + Recall Gate + Replay + Turn Planner）
2. Phase 0の完了条件に「面白かったか」がない（I-1）
3. 受け入れ条件がPhaseを追い越している（II-3）
4. **Phase 2全体が§5.10と§21.1に反している。** 2つ目のRuleset / Scenario形式 / Provider、Profile、Manifest、Hook、Migration、開発者ドキュメント。これは「フレームワークを先に完成させる」作業そのもので、しかも「自分が遊びたい」に一つも寄与しない

### 推奨順序

| | 内容 | 完了条件 |
|---|---|---|
| **Phase A** | V-2の最小構成。1プロンプト／構造化出力／可視Canon投入＋Evidence検証／ダイス／HP／クロック1本／選択肢／Streaming／セーブ＋あらすじ／生ログ／コスト表示／1〜2時間シナリオ1本 | **自分で最後まで通しで遊び、翌日もう一度遊びたいと思った。** 思わなかった場合、Canon Ledgerを作らずに済んだことが最大の成果 |
| **Phase B** | **10〜20時間実際に遊び、破綻を記録する。記録された破綻の頻度順にだけ直す。** 併せて、入力列をファイルから流すヘッドレスドライバを作る（II-3の合成データテストと、モデル変更時の比較の両方に効く） | 同じシナリオを2周、または2本目のシナリオを完走 |
| **Phase C** | ここで初めて Recall Gate / 検索 / 要約 / 訂正 / superseded を作る。**Canonが1000件規模を超えてから** | 10セッション規模のキャンペーンで、5セッション前の約束を根拠付きで参照できた |
| **Phase D以降** | Web化（Phase Aで単一HTMLにしていれば不要）、2つ目のルールセット、複数人 | 到達したら考える |
| **現Phase 2** | **削除** | 拡張性を証明する相手がいない。抽象化は「2つ目が必要になった時にその場でリファクタする」で足りる |

**核心の入れ替え: 現行は「Canon Ledgerを設計してから遊ぶ」。推奨は「遊んでからCanon Ledgerを設計する」。**

Phase Bで記録される実際の破綻が、§10.2 L2のどのフィールドが本当に必要かを教えてくれる。今それを机上で決めると、13種のEpistemic Statusのうち3種しか使わなかった、という結果になる可能性が高い。

**予想される破綻の頻度順（あくまで予想であり、実測で覆るべきもの）**:
1. 直近3〜10ターンの事実の忘却 → 事実テーブルの整備と検索
2. NPCが受け身で世界が動かない → クロックとNPC目標の強化
3. 文章が冗長で読み飛ばす → 出力長の制御
4. テンポが遅い → キャッシュとプロンプト構成
